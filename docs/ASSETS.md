# Assets

Everything the game draws comes from five packed atlases under `public/sprites/`,
declared in `src/game/assets/manifest.ts`. Nothing else is loaded at runtime.

| Atlas | Contents | Frames | Size |
|---|---|---|---|
| `terrain.png` | seamless ground tiles | 9 | 28 KB |
| `world.png` | props, buildings, resources, effects | 69 | 52 KB |
| `items.png` | inventory icons | 104 | 20 KB |
| `characters.png` | 15 sprite sheets, 4 facings × N frames | 15 | 176 KB |
| `ui.png` | HUD icons | 6 | 4 KB |

**203 frames, 0.27 MB** against a 3.5 MB budget. The previous set was 2.61 MB
for fewer assets; the saving is not compression, it is that art made of nine
colours compresses like nine colours.

Every texture is generated by **Hearthwood**, a deterministic Python pipeline in
`tools/hearthwood/`. Nothing is hand-drawn and nothing calls a model. Given the
same seeds it produces byte-identical PNGs, which is why the art can be rebuilt
in 17 seconds and reviewed as a diff.

---

## The rule the whole pipeline exists to enforce

**Paint an index map, not colours.**

Every generator builds a 2D array of integers — ramp step 0..8 — and only at the
very end does that array get looked up in a ramp. Nothing anywhere in the
pipeline writes a free RGB value into a texture. This is what makes the set
cohere: two materials drawn by two different scripts on two different days
cannot drift apart in hue, contrast or light direction, because neither one ever
chose a colour. They chose a *step*, and the ramp chose the colour.

The one thing that does touch RGB is the final grade, and it runs over
everything identically.

## Palettes

`tools/hearthwood/palettes.py` is the single source of colour.

- **`REFERENCE`** holds the ten given ramps verbatim — `oak_wood`,
  `spruce_wood`, `oak_bark`, `dark_bark`, `stone`, `dirt`, `path`, `pebble`,
  `moss`, `smoke`. New materials reuse these wherever they plausibly can; a
  crate and a floorboard should be the same wood.
- **`_DERIVED_SOURCES`** holds 33 more materials as three or four anchor
  colours each. `build_ramp` sorts them by OKLab lightness, resamples to 7–9
  steps *in Lab* (not RGB — an RGB midpoint between two saturated colours goes
  grey and muddy through the middle), and clamps the ends.

Every ramp obeys the same four constraints:

| | |
|---|---|
| Length | 7–9 steps, dark → light |
| Hue shift | −6° at the darkest step to +6° at the lightest, in OKLab |
| Floor / ceiling | `#1c120b` and `#fff7e6` — no pure black, no pure white |
| Chroma | +7%, but **weighted by existing chroma** so greys stay grey |

That last one is the subtle one. Applying a flat hue rotation to a neutral grey
turns it into a tinted grey, and a stone ramp that has drifted lilac is
immediately obvious next to one that hasn't. So the rotation is scaled by how
much chroma a colour already has:

```python
weight = np.clip(lch[..., 1] / 0.06, 0.0, 1.0)
lch[..., 2] = (lch[..., 2] + degrees * weight) % 360.0
```

A near-neutral takes almost none of the shift; a saturated colour takes all of
it.

## The pipeline

`tools/hearthwood/hw/core.py`. Every material runs the same five stages.

**1. Noise, always periodic.** Value noise on a lattice, cubic-interpolated,
with the lattice wrapping. Two or three octaves, persistence ~0.55. Wrapping is
not an afterthought applied at the end — a texture made from wrapping noise is
seamless *by construction*, so there is no cross-fade band down the middle where
a blend used to be.

**2. Quantise onto the middle steps.** The body of a material uses only 3–4
steps out of the ramp's 7–9. The extremes are held back deliberately, for
edges, cracks, and specular hits. A texture that uses its whole ramp for its
base noise has nothing left to draw an edge with, and reads flat and busy at the
same time.

**3. Material recipe.** The part that is actually different per material:
plank seams and end grain, bark fissures running with the trunk, the growth
rings of a log end, Voronoi cobbles with mortar, brick courses with a half-brick
offset, soil clods, grass blades, leaf clumps, moss creeping up from the base,
smoke, woven cloth, hammered metal. In `hw/materials.py`, `hw/props.py`,
`hw/architecture.py`, `hw/icons.py`.

**4. Declump.** No lone pixels. A pixel whose value matches none of its
neighbours is noise, not texture, and at this palette size it reads as dirt on
the screen. `declump` iterates to a fixed point, and breaks ties by *value*
rather than position:

```python
score[i] = agree * (1 << 24) + stack[i]
```

Position-based tie-breaking sounds harmless and is not: it makes the result
depend on scan order, which means a sprite and its mirror declump differently
and a character's left side stops matching their right.

**5. Grade.** One OKLab pass over every texture in the game, identical
parameters, no exceptions:

- contrast ×0.96 about mid-grey
- `L = L * 0.965 + 0.03` — lifts the blacks, drops the whites
- warm white balance
- per-hue chroma: reds ×1.08, yellows ×1.04, pinks ×1.04, greens ×1.07 and
  rotated 4° toward yellow-green, blues ×0.97
- near-neutrals take only part of the warmth

This is the stage that makes a pine tree and an iron ingot look like they were
lit by the same afternoon.

## Light

**One light, upper left, everywhere.** Not a convention the scripts are asked
to respect — a parameter they share. Nothing in the set is lit from anywhere
else, which is why the terrain renderer may rotate a ground tile by a hash of
its position but must not rotate a plank floor: `structured` in
`TerrainRenderer.ts` exempts anything whose lighting has a direction in it.

A consequence worth stating because it looks like a bug: **a character's left
and right facings are not mirror images of each other.** The *geometry* is
mirrored — that is tested, across every frame of all 15 sheets — but the shading
is not, because the sun does not move when the character turns around. A
perfectly mirrored sprite pair is the actual error.

## Characters are one model, rotated

`tools/hearthwood/hw/model.py` and `characters.py`.

A character is not four drawings. It is a set of ellipsoid parts — head, torso,
limbs, ears, tail — positioned in 3D, rotated about the vertical axis for each
facing, and painted back to front by depth. The four rows of a sheet are the
same model at 0°, 90°, 180°, 270°.

This is the only way to get what was asked for: the same character from every
angle. Drawing four sprites and hoping they match does not survive the third
character.

The walk cycle is procedural too — limb swing by phase, a body bob, a lean into
travel — so adding a frame is a number, not a drawing. `silhouette()` exposes
the pre-shading geometry so tests can assert on the model rather than on pixels.

One subtlety: parts from different ramps must be declumped *jointly*, keyed on
`ramp_id * 64 + step`, because step 4 of the cloth ramp and step 4 of the skin
ramp are different colours and treating them as equal merges a sleeve into an
arm.

## Checks, run on every build

`build_all.py` fails the build on any of these:

- **Colour count** — a texture may use its ramp and at most two accents.
  Budgeted *per material*, so a house with plaster, timber, shingle and glass is
  allowed four ramps and a cottage is not allowed four by accident.
- **Lone pixels** — must be zero.
- **Seams** — every seamless texture is compared against itself tiled, and the
  seam edge must be weaker than the texture's own strongest interior edge. An
  absolute threshold is meaningless here: 2.0 is a catastrophe on smooth sand
  and invisible on cobblestone. The metric is validated against deliberately
  broken control tiles, because a seam check that passes everything is worse
  than no seam check.
- **Mirror symmetry** — character geometry, per frame.

`contact_sheet.py` then renders the review artifact: `docs/contact/hearthwood.png`,
three panels — every asset labelled at 8× nearest-neighbour, every seamless tile
at 3×3, and the ground materials on isometric cubes so the light direction can be
checked on three faces at once.

## Sizes are authored, never derived

Authored as **world units** in `src/game/assets/manifest.ts`. Pixel size is
derived from them, at build time, in one direction only:

```
manifest.ts  →  dump-world-sizes.mjs  →  world_sizes.json  →  generator
                                                                  ↓
frames.ts    ←     pack-atlases.mjs    ←    the actual PNG files
```

The generator asks the manifest how big a thing is in the world and picks a
pixel height from it; the packer reads pixel sizes back off the files it is
packing. Neither ever guesses. This closed the six aspect-ratio mismatches
between art and manifest that the previous pipeline had accumulated, and makes
the class of bug structurally impossible rather than merely fixed.

Terrain is 128×128 and seamless. Items are 128×128. Props are 128 wide by
whatever their world aspect implies, rounded to a multiple of 4 and clamped to
64–256.

## Colliders are authored, not traced

Colliders were once generated at runtime by reading sprite pixels: slow,
non-deterministic, and it meant regenerating art silently changed physics.

They are authored in `manifest.ts` as ellipses at an object's base, sized to its
*footprint* rather than its silhouette — a tree's canopy should not block
movement, only its trunk. `scripts/suggest-collider.mjs` proposes numbers from
the alpha channel for a new asset; a human pastes them in. Art never feeds
physics.

Hit testing for *clicks* is separate and lives in `src/game/systems/picking.ts`
— see `docs/DESIGN.md`.

## Rebuilding everything

```bash
npm run assets:all
```

which is:

```bash
npm run assets:sizes   # manifest.ts       -> tools/hearthwood/world_sizes.json
npm run assets:art     # generators        -> assets-build/
npm run assets:pack    # assets-build/     -> public/sprites/ + frames.ts
npm run assets:sheet   # assets-build/     -> docs/contact/hearthwood.png
npm run audit:assets   # must report 0 missing, 0 unused
```

About 17 seconds, no network, no credentials, no API key. The output is
deterministic: if nothing in `tools/hearthwood/` changed, `git status` is clean
afterwards.

## Adding one new asset, end to end

1. **Author its world size and collider** in `src/game/assets/manifest.ts`:

   ```ts
   'world/anvil': solid(110, 120, 32, 14),   // worldSize w,h then collider rx,ry
   ```

2. **Write its recipe.** A function in `hw/props.py` (or `materials.py`,
   `icons.py`, `architecture.py`) that returns an index map plus which ramp to
   look it up in. Reuse an existing ramp unless the material genuinely is a new
   one.

3. **Register it** in the relevant `gen_*.py`:

   ```python
   add('anvil', TALL, lambda w, h, s: anvil_prop(w, h, s), 3042, materials=2)
   ```

   The size argument resolves through `frame_for()`, which reads the world size
   you authored in step 1. `materials=` is the colour budget: how many ramps
   this asset is allowed.

4. **Build and look at it.** `npm run assets:art && npm run assets:sheet`, then
   open `docs/contact/hearthwood.png`. Reviewing assets side by side is the only
   way to catch the drift this whole pipeline exists to prevent.

5. **Pack it:** `npm run assets:pack`.

6. **Point the game at it** — if it is a placeable entity, add a case to
   `idForEntity()` in `src/game/assets/colliders.ts`. Nothing looks assets up by
   filename, so that is the only wiring needed.

7. `npm run audit:assets` must still report 0 missing, 0 unused.

## Engine import

Point/nearest filtering, no compression, mipmaps off. This matters more for this
art than for most — see **[docs/IMPORT.md](IMPORT.md)**.

## The generated files

`assets-build/` holds the generated frames (263 files) and `public/sprites/`
the packed atlases. Both are committed, because the generator is deterministic
— an art diff is a real review artifact rather than noise, and a clone builds
and runs without a Python toolchain. `assets-src/`, the previous pipeline's raw
model output, is gitignored.

### The previous pipeline

Art used to be generated through Replicate and rescued in post — chroma-key
background removal, flood fill, trim, outline, baked contact shadow. The scripts
still exist (`assets:generate`, `assets:process`, `scripts/lib/replicate.mjs`,
`scripts/mcp/replicate-asset-server.mjs`) and still work, but nothing shipped is
made by them. They are kept because they are the only way to get a *painterly*
asset if one is ever wanted, not because the game needs them.

If you do run it, `REPLICATE_API_TOKEN` goes in `.env.local`, which is
gitignored. It must never be committed.
